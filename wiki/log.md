- **2026-06-01** — Unit refactor: model is now **cycle-based bottom-up**. The architectural source numbers are natively per-cycle (e.g. "1 dwordx16 / cycle = 64 B/cycle" for VMEM, "660 ns RTT @ 2 GHz = 1320 cycles" for xGMI); pre-multiplying by `clock_ghz` to expose ns values obscured the underlying physics and made it harder to retarget the model to a different clock (overclock studies, future architectures). `Hardware` and `CommHardware` fields are now expressed in cycles (`xgmi_latency_cycles`, `atomic_latency_cycles`, `launch_overhead_cycles`) and bytes/cycle (`hbm_read_bw`, `tcp_bw`, `link_bw`, etc.); `WgTileLatencyBreakdown.*_cycles` fields are the source of truth, with legacy `T_*` properties returning ns for backward-compat display. `compute_collective_latency` returns GPU cycles; the cycles→µs conversion lives at exactly one point (`predict_row` divides by `clock_ghz * 1000`). Framework overhead (`heuristics.framework_overhead_ns`) stays in **host wall-time ns** — it is unrelated to the GPU clock and would not scale with `clock_ghz`. Dashboard reads ns via convenience properties (`hw.xgmi_latency_ns`, `comm_hw.link_bw_ns`, `hw.hbm_read_bw_per_cu_ns(...)`, etc.). Verified byte-identical across 243 predictions (0.0 µs max absolute error vs pre-refactor baseline); all 87 tests pass; dashboard renders clean.
